# Календарь маркировки V2 — проектная спецификация

- Дата: 2 сентября 2026 года
- Статус: дизайн согласован, готов к составлению плана реализации
- Продукт: «Календарь маркировки»
- Репозиторий: `marking-calendar`
- Платформа первой версии: Windows

## 1. Контекст

Текущая версия — небольшое локальное приложение на HTML, CSS и JavaScript с PowerShell-установщиком, запуском и обновлением. Она решает основную задачу, но усложняет дальнейшее сопровождение:

- бизнес-логика частично дублируется между JavaScript и PowerShell;
- тесты проверяют отдельный модуль, который не полностью совпадает с рабочим кодом;
- запуск через PowerShell может кратковременно показывать окно терминала;
- обновление данных недостаточно защищено от пустого или повреждённого ответа;
- интерфейс перегружен поясняющими подписями, а значение цветов календаря неочевидно;
- отсутствует единый штатный механизм установки, обновления и публикации релизов.

Так как проект небольшой, поддерживаемость важнее сохранения текущей реализации. V2 создаётся как чистое Windows-приложение без переноса старой архитектуры.

## 2. Цели

V2 должна:

1. Запускаться как обычное Windows-приложение без окна терминала.
2. Сразу показывать последний доступный календарь, не заставляя пользователя ждать обновления.
3. Безопасно обновлять данные в фоне и наглядно сообщать о содержательных изменениях.
4. Иметь один источник бизнес-логики и хорошо проверяемое ядро.
5. Быть простой в сопровождении, сборке и публикации на GitHub.
6. Поддерживать автоматическое обновление самого приложения через GitHub Releases.
7. Иметь понятную легенду цветов, лаконичный интерфейс и доступную навигацию.
8. Сохранять рабочие данные текущей версии при переходе на V2.

## 3. Не входит в первую версию

- поддержка macOS и Linux;
- облачная учётная запись и синхронизация между устройствами;
- серверная часть, аналитика и телеметрия;
- редактирование официальных событий пользователем;
- магазин приложений Microsoft Store;
- обязательная цифровая подпись установщика на первом публичном релизе.

Цифровая подпись желательна в дальнейшем, но отсутствие сертификата не блокирует первую публикацию.

## 5. Технологический стек

- .NET 10 LTS;
- WPF как нативная оболочка Windows;
- WebView2 для календаря и связанных экранов;
- TypeScript, HTML и CSS для интерфейса внутри WebView2;
- C# для всей бизнес-логики, хранения, сети, сравнения данных и обновления;
- Velopack для установки и обновления приложения из GitHub Releases;
- встроенная система тестирования .NET и тесты TypeScript-интерфейса.

WebView2 отвечает только за отображение и пользовательские события. TypeScript не должен повторять нормализацию, сравнение, валидацию, хранение или правила классификации событий.

## 7. Основной пользовательский сценарий

1. Пользователь запускает `MarkingCalendar.exe`.
2. Приложение немедленно открывает календарь из последнего проверенного локального снимка.
3. Если локального снимка ещё нет, используется снимок, встроенный в установочный пакет.
4. Проверка новых данных начинается в фоне и не блокирует интерфейс.
5. Компактный индикатор сообщает состояние: проверка, данные актуальны, обновлено или ошибка.
6. Если содержательных изменений нет, приложение не отвлекает пользователя.
7. Если изменения есть, появляется одно внутреннее всплывающее окно с их сводкой.
8. При ошибке остаётся доступен последний корректный календарь и действие «Повторить».

Отдельное окно проверки обновлений и системный `MessageBox` не используются.

## 8. Уведомление об изменениях данных

После успешного сравнения нового снимка с текущим приложение показывает внутри главного окна уведомление «Календарь обновлён».

Уведомление содержит:

- количество перенесённых событий;
- количество добавленных событий;
- количество изменённых событий;
- количество удалённых событий;
- до восьми наиболее важных изменений;
- кнопки «Все изменения», «Скопировать» и «Закрыть».

Приоритет списка: ближайшие по дате изменения, затем переносы, изменения, добавления и удаления. Одно и то же обновление показывается только один раз. Повторный запуск приложения не должен заново показывать уже просмотренную сводку.

«Все изменения» открывает журнал, отфильтрованный по текущему пакету обновления.

Если пользователь выбрал товарные группы, сводка отдельно считает изменения в них и в остальных группах. Обновление только по остальным группам не открывает модальное окно: показывается компактное уведомление, а пакет сразу считается просмотренным. Журнал по умолчанию открывается в режиме «Мои группы», но позволяет явно показать все факты.

Журнал хранит добавления, переносы, правки формулировок и удаления. Для изменённого текста доступно сравнение «было / стало» с текстовыми обозначениями, зачёркиванием удалённого и подчёркиванием добавленного. Любой пакет и временное сравнение с сохранённым снимком можно скопировать как одну и ту же ограниченную по размеру текстовую сводку. Сравнение с архивом не создаёт новый пакет истории и не меняет рабочий снимок.

## 9. Календарь, фильтры и легенда

Легенда не дублируется отдельным тяжёлым блоком. Текущие фильтры категорий одновременно выполняют роль легенды:

- рядом с названием категории отображается цветная точка, совпадающая с цветом событий этой категории;
- выбранное и отключённое состояние визуально различимы не только цветом;
- элементы доступны с клавиатуры и имеют понятные подписи для экранного диктора;
- для цветов обеспечивается достаточный контраст.

Статусы изменений — «Новое», «Перенос», «Изменено» — показываются отдельной компактной легендой только там, где эти статусы присутствуют. Их нельзя кодировать исключительно цветом: статус сопровождается текстом или значком.

События, добавленные или перенесённые в течение последних 60 дней, получают текстовые бейджи прямо в календарной ленте. Фильтр «Только с изменениями» оставляет только такие карточки. В drawer события показывается проверяемая хронология от новых записей к старым: дата обнаружения, прежняя дата или формулировка, число переносов и дата первого появления, если она известна.

Маркер события и его карточка должны быть доступны мышью, клавиатурой и средствам специальных возможностей.

## 10. Текст интерфейса

Интерфейс использует короткие нейтральные формулировки. Удаляются декоративные и назидательные подсказки, не помогающие выполнить действие.

В частности:

- подпись «Локальный мониторинг» не используется;
- поясняющий текст над историей изменений удаляется;
- пустое состояние истории: «Изменений пока нет»;
- ошибки содержат причину в понятной форме и доступное действие;
- технические подробности доступны отдельно и не перегружают основной экран.

## 11. Получение и проверка данных

Новый ответ источника никогда не становится рабочим снимком только потому, что HTTP-запрос завершился успешно.

Перед сохранением выполняются:

1. проверка формата документа и версии схемы;
2. проверка обязательных полей каждого события;
3. нормализация дат, идентификаторов, категорий и типов;
4. проверка уникальности устойчивых идентификаторов;
5. проверка разумного диапазона дат;
6. проверка аномального изменения общего количества событий;
7. построение и проверка набора изменений.

Пустой ответ, повреждённый документ или аномальный обвал количества событий не заменяет текущий снимок. Такой ответ сохраняется только как диагностическая информация с ограниченным сроком хранения, а пользователю показывается неразрушающая ошибка.

Порог аномалии задаётся конфигурацией и покрывается тестами. Для намеренного крупного изменения источника должен существовать явный безопасный путь принятия нового снимка после проверки, а не отключение валидации в коде.

## 12. Хранение данных

Рабочие данные располагаются вне каталога установки в `%LOCALAPPDATA%\KRS\MarkingCalendar`.

Минимальная структура:

- `data/current.json` — последний проверенный снимок;
- `data/bundled.json` — копия начального снимка для диагностики;
- `history/` — журнал содержательных обновлений;
- `archive/` — ограниченный набор предыдущих проверенных снимков;
- `logs/` — технические журналы;
- `state.json` — версия хранилища и идентификатор последнего показанного обновления.

Все замены рабочего снимка выполняются атомарно: запись во временный файл, проверка чтением и безопасная замена. При сбое питания или завершении процесса предыдущий корректный снимок остаётся доступен.

Архив и журналы имеют ограничения по количеству файлов, возрасту и суммарному размеру. Очистка не затрагивает текущий снимок и последний диагностически полезный журнал.

## 13. Переход с текущей версии

При первом запуске V2 приложение проверяет `%LOCALAPPDATA%\CHZ-MarkingCalendar`.

Если данные найдены:

1. они читаются без изменения исходных файлов;
2. проходят нормализацию и валидацию V2;
3. корректный снимок и совместимая история импортируются в новое хранилище;
4. результат импорта записывается в журнал;
5. старый каталог остаётся на месте.

Повторный запуск не дублирует импорт. Автоматическое удаление данных прежней версии не выполняется.

## 14. Обновление приложения

Проверка новой версии приложения выполняется отдельно от обновления календарных данных.

- источник релизов — официальный репозиторий KRS на GitHub Releases;
- проверка выполняется в фоне после запуска;
- загрузка не блокирует работу с календарём;
- установка применяется при следующем запуске или после явного согласия на перезапуск;
- сбой обновления не повреждает установленную версию;
- пользователь видит номер текущей и доступной версии;
- приложение не принимает пакеты обновлений из сторонних репозиториев.

Официальными бинарными сборками считаются только файлы из GitHub Releases указанного в приложении репозитория.

## 19. CI и выпуск релизов

GitHub Actions запускается при каждом push и pull request и выполняет:

- восстановление зависимостей;
- сборку C# с предупреждениями, контролируемыми проектом;
- модульные и интеграционные тесты .NET;
- установку фиксированной версии Node.js;
- сборку TypeScript;
- тесты интерфейса;
- проверку форматирования и статического анализа.

Релиз создаётся по тегу `vX.Y.Z`. Процесс собирает установщик, portable-архив и служебные файлы Velopack, рассчитывает SHA-256 и прикладывает артефакты к GitHub Release. Публикация не должна зависеть от файлов, вручную собранных на рабочем компьютере.

## 21. Стратегия тестирования

### Доменное ядро

- одинаковые снимки не создают изменений;
- добавление, удаление, перенос и изменение распознаются отдельно;
- порядок входных элементов не влияет на результат;
- нормализация повторяема;
- некорректные даты и обязательные поля отклоняются;
- крупное аномальное изменение блокируется.

### Хранилище и сеть

- пустой или повреждённый ответ не заменяет рабочий снимок;
- атомарная запись переживает искусственно прерванную операцию;
- очистка архива соблюдает лимиты;
- миграция повторяема и не меняет старые файлы;
- при отсутствии сети запускается последний корректный снимок.

### Интерфейс

- приложение открывает календарь до окончания фоновой проверки;
- фильтры и события доступны с клавиатуры;
- цветовая легенда соответствует маркерам;
- статус различим без опоры только на цвет;
- уведомление показывается один раз на пакет изменений;
- «Все изменения» открывает правильный набор;
- ошибки не закрывают доступ к последним данным.

### Установка и обновление

- чистая установка;
- обновление поверх предыдущей версии;
- запуск после обновления;
- сохранение локальных данных;
- проверка Setup и Portable на поддерживаемой версии Windows.

## 22. Критерии приёмки V2

V2 готова к первому публичному релизу, если одновременно выполнены следующие условия:

1. Приложение запускается с ярлыка без видимого окна терминала.
2. На первом запуске доступен встроенный календарь, а на последующих — последний проверенный снимок.
3. Фоновая проверка не блокирует интерфейс.
4. Повреждённые, пустые и аномальные ответы не заменяют рабочие данные.
5. Все типы изменений определяются единственным C#-ядром и покрыты тестами.
6. Пользователь получает одно понятное уведомление о новом пакете изменений.
7. Фильтры одновременно служат понятной легендой цветов.
8. Основные действия доступны с клавиатуры, а статусы различимы без цвета.
9. Импорт прежних данных не удаляет и не изменяет старое хранилище.
10. Установка и обновление приложения не требуют PowerShell-лаунчера.
11. CI собирает проект и выполняет все тесты на чистом окружении.
12. GitHub Release создаёт Setup, Portable, SHA-256 и служебные файлы автообновления из тега версии.
13. README, лицензия, сведения о разработчике и страница поддержки оформлены до публикации.

## 23. Последовательность реализации

После отдельного утверждения плана реализация должна идти вертикальными проверяемыми этапами:

1. каркас решения и доменные модели;
2. перенос нормализации, валидации и сравнения в тестируемое C#-ядро;
3. хранилище, источник данных и безопасное обновление снимка;
4. WPF-оболочка и минимальный мост WebView2;
5. календарь, легенда, история и уведомление об изменениях;
6. миграция текущих данных;
7. поддержка, «О программе» и финальная редактура текста;
8. установщик и обновление через Velopack;
9. CI, README, лицензия и первый тестовый GitHub Release;
10. итоговое ревью архитектуры, доступности, безопасности и сценариев обновления.

Каждый этап должен завершаться тестами и проверяемым рабочим состоянием, а не большой интеграцией в конце.
