# Участие в разработке

Спасибо за интерес к «Календарю маркировки».

## Ошибки

Создайте Issue по шаблону и укажите:

- версию приложения и Windows;
- Setup или Portable;
- последовательность действий;
- ожидаемое и фактическое поведение;
- воспроизводится ли ошибка после перезапуска.

Не прикладывайте персональные данные. Журнал можно открыть через `Справка` → `О программе` → `Открыть журнал`. Перед публикацией `app-*.log` проверьте его содержимое; файлы `rejected-*.json` по умолчанию не прикладывайте.

## Изменения кода

1. Сначала создайте Issue для изменений поведения или архитектуры.
2. Делайте один связный набор изменений в одном pull request.
3. Классификацию, подписи типов, список групп и сохраняемый выбор держите в C#. Фильтрацию, визуальную группировку и расчёт блока «Ближайшее» держите в TypeScript и покрывайте Vitest-тестами.
4. Добавляйте тест на исправленную ошибку или новое поведение.
5. Не меняйте адреса источника данных, GitHub и CloudTips в нескольких местах: используйте существующие константы и модели.
6. Не добавляйте телеметрию, рекламу или сетевые зависимости без отдельного обсуждения.

Перед pull request выполните:

```powershell
dotnet test MarkingCalendar.slnx -p:SkipUiBuild=true
Push-Location src/MarkingCalendar.UI
npm ci
npm test -- --run
npm run build
Pop-Location
pwsh -File build/test-update-bundled.ps1
```

Чтобы проверить обновление встроенных данных из официального источника, запустите `pwsh -File build/update-bundled.ps1`. Релизные ресурсы обновляются из проверенной ветки `data` командой `pwsh -File build/update-bundled.ps1 -FromPublic`; при этом снимок, метаданные и история заменяются вместе. Не меняйте эти файлы вручную по отдельности.

## Публичная история календаря

Автоматическая публикация выполняется на self-hosted runner под Linux с российским IP-адресом. Подготовка runner описана в [docs/self-hosted-runner.md](docs/self-hosted-runner.md). GitHub-hosted runner использовать нельзя: официальный источник отвечает ему HTTP 403.

Без записи файлов проверить источник локально можно так:

```powershell
dotnet run --project src/MarkingCalendar.Runner/MarkingCalendar.Runner.csproj -c Release -- check --data build/.work/history-data --dry-run
```

Ручной запуск публикации выполняется на GitHub во вкладке Actions → `Public calendar history` → `Run workflow` либо через GitHub CLI. Он начнётся только при подключённом self-hosted runner с меткой `marking-calendar`; без runner запуск останется в очереди.

```powershell
gh workflow run history.yml --ref main
gh run watch
```

Если пришло уведомление о падении workflow:

1. Откройте упавший запуск и скачайте artifact `rejected-calendar-response`.
2. Сравните отклонённый ответ с текущей страницей и официальными публикациями «Честного знака». Не принимайте крупное сокращение данных только ради зелёного CI.
3. Если массовое изменение подтверждено как легитимное, получите ветку `data` локально и один раз запустите раннер с явным исключением:

```powershell
git fetch origin data
git worktree add build/.work/history-data origin/data
dotnet run --project src/MarkingCalendar.Runner/MarkingCalendar.Runner.csproj -c Release -- check --data build/.work/history-data --accept-anomaly
```

После этого проверьте `current.json`, `manifest.json`, `CHANGELOG.md` и `history/changes.json` глазами до публикации. `--accept-anomaly` разрешает только аномалию числа событий; остальные ошибки формата и обязательных полей по-прежнему блокируют обновление.

## Разметка новых товарных групп

Основная карта отраслей хранится в `assets/groups/groups.json`. Ветка `data` и встроенный ресурс приложения получают точную копию этого файла; содержимое копий вручную не редактируйте.

Чтобы разметить новую группу:

1. Найдите её точные `name` и `link` в текущем снимке «Честного знака».
2. Добавьте в массив `groups` один объект с этими значениями и непустым массивом `sectors`. Идентификаторы отраслей берите из массива `sectors` в начале того же файла. Одну группу можно отнести к нескольким отраслям.
3. Если проект завершён, добавьте `"status": "completed"`; другие значения статуса не поддерживаются.
4. Обновите `updatedAt`, запустите `pwsh -File build/update-bundled.ps1` и убедитесь, что `Resources/bundled-groups.json` совпадает с основной картой.

При публикации workflow запускает:

```powershell
dotnet run --project src/MarkingCalendar.Runner/MarkingCalendar.Runner.csproj -c Release -- validate-groups --data ./data
```

В Job summary отдельно перечисляются группы снимка, которых ещё нет в карте, и записи карты, отсутствующие в снимке. Эти списки не означают падение проверки. Неразмеченная новая группа всё равно предлагается всем пользователям, поэтому задержка разметки не скрывает её; после проверки карту можно дополнить обычным отдельным pull request.
